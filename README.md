# Logivio Backend - النموذج الأولي

خلفية Node.js/Express لمنصة Logivio، تغطي نطاق النموذج الأولي (MVP) وتوسعة "البوابات":
إدارة المواعيد والسعة، منع تعارض الحجز، **طابور مستقل لكل بوابة دخول** ثم **طابور مستقل لكل رصيف**
(بدل طابور واحد عام للمصنع)، التسجيل عبر QR على مرحلتين (وصول للبوابة ثم دخول فعلي)، ولوحة مؤشرات أساسية.

## لماذا طابوران منفصلان (بوابة ثم رصيف)؟

في الواقع الميداني، الاختناق يحدث في نقطتين مختلفتين تمامًا:
1. **البوابة**: نقطة دخول فيزيائية مشتركة بين كل الشاحنات (فحص، وزن، مسح QR) - عنق الزجاجة هنا هو عدد البوابات المتاحة، بغض النظر عن وجهة الشاحنة لاحقًا.
2. **الرصيف**: بعد الدخول، الشاحنة قد تنتظر تحرر رصيفها المحدد بالذات - عنق الزجاجة هنا خاص بكل رصيف على حدة.

لذلك تدفق الشاحنة الفعلي في هذا الإصدار: `PATCH /checkins/:id/arrive` (وصول فيزيائي، يوزَّع تلقائيًا على أقل بوابة ازدحامًا) ← `PATCH /checkins/:id/entry` (انتهت معالجة البوابة، تُحرَّر البوابة ويُفحص الرصيف) ← `start` ← `finish`.

## التشغيل

1. `npm install`
2. انسخ `.env.example` إلى `.env` واملأه بمعلومات الاتصال بقاعدة MySQL على Clever Cloud، وضع قيمة عشوائية طويلة لـ `JWT_SECRET`.
3. **مهم**: نفّذ ملفات الترحيل التالية بالترتيب على نفس قاعدتك (لا تحذف أي بيانات):
   - `migration_002_gates.sql` (البوابات والطوابير المنفصلة)
   - `migration_003_auth_and_settings.sql` (توسيع الأدوار + بيانات صاحب المصنع)
4. `npm start` أو `npm run dev`.

الخادم يعمل افتراضيًا على المنفذ 3000: http://localhost:3000

## المصادقة (Auth)

كل المسارات التشغيلية (المواعيد، البوابات، الأرصفة، الطابور...) لا تزال مفتوحة في هذا الإصدار لتسهيل الاختبار، عدا **تعديل إعدادات المصنع** الذي يتطلب تسجيل دخول بدور `admin`. أرسل الرمز في ترويسة كل طلب محمي:

```
Authorization: Bearer <token>
```

| المسار | الطريقة | الوصف |
|---|---|---|
| `/api/auth/register` | POST | إنشاء حساب (`fullName`, `email`, `password`, `role`) — الأدوار: `driver`, `gate_agent`, `dock_operator`, `admin` |
| `/api/auth/login` | POST | تسجيل الدخول (`email`, `password`) — يُعيد `token` و`user` |
| `/api/auth/me` | GET | بيانات المستخدم الحالي من الرمز (لاستعادة الجلسة) |
| `/api/facilities/:id` | GET | بيانات المصنع (الاسم، صاحب المصنع، هاتفه، العنوان، ساعات العمل) |
| `/api/facilities/:id` | PATCH | تعديل إعدادات المصنع — **يتطلب تسجيل دخول بدور admin** |

## نقاط النهاية (API Endpoints)

| المسار | الطريقة | الوصف |
|---|---|---|
| `/api/docks?facilityId=1` | GET | حالة كل الأرصفة |
| `/api/docks/:id/status` | PATCH | تغيير حالة رصيف (available/busy/maintenance) |
| `/api/gates?facilityId=1` | GET | حالة كل البوابات |
| `/api/gates/:id/status` | PATCH | تغيير حالة بوابة يدويًا |
| `/api/appointments?date=YYYY-MM-DD` | GET | مواعيد يوم معيّن |
| `/api/appointments` | POST | إنشاء موعد جديد (يتحقق تلقائيًا من ساعات العمل، تعارض الرصيف، والسعة اليومية) |
| `/api/appointments/:id/cancel` | PATCH | إلغاء موعد |
| `/api/queue?facilityId=1&type=dock&dockId=2` | GET | طابور رصيف معيّن (أو كل طوابير الأرصفة إن حُذف dockId) |
| `/api/queue?facilityId=1&type=gate` | GET | طابور بوابة معيّنة أو كل طوابير البوابات |
| `/api/queue/:id/remove` | PATCH | استدعاء شاحنة من طابورها (بوابة أو رصيف) |
| `/api/checkins/scan/:qrCode` | GET | جلب بيانات الموعد بعد مسح QR |
| `/api/checkins/:id/arrive` | PATCH | **جديد**: وصول فيزيائي، يوزَّع تلقائيًا على أقل بوابة ازدحامًا أو يدخل طابور البوابة |
| `/api/checkins/:id/entry` | PATCH | انتهاء معالجة البوابة: تُحرَّر البوابة، ويُضاف للطابور تلقائيًا إذا كان الرصيف مشغولاً |
| `/api/checkins/:id/start` | PATCH | بداية عملية التحميل/التفريغ |
| `/api/checkins/:id/finish` | PATCH | إنهاء العملية وتحرير الرصيف |
| `/api/checkins/:id/delay-reason` | POST | تسجيل سبب تأخير |
| `/api/dashboard/stats?facilityId=1&date=YYYY-MM-DD` | GET | مؤشرات اليوم |

## ملاحظة

تم اختبار كل هذا التدفق فعليًا (3 شاحنات، بوابتان، رصيف مشغول) على قاعدة MySQL محلية قبل التسليم:
توزيع تلقائي على أقل بوابة ازدحامًا، دخول شاحنة ثالثة لطابور البوابة عند امتلاء الاثنتين، تحرير البوابة عند اكتمال المعالجة، واستدعاء ناجح من الطابور - كل ذلك عمل دون أخطاء.
